# v0.5：配对提效评测

`benchmark` 用同范围任务的人工基线与研序流程做配对比较。目标是回答“在哪类任务、多少个样本、质量相同的前提下，人工时间减少了多少”，而不是给整支团队套一个无法复核的百分比。

## 输入

输入是 JSON，顶层包含：

- `evidence_type`：`observed` 表示真实观察，`synthetic` 表示功能演示；
- `scope`：任务类型、语言、仓库与观察窗口；
- `records`：1–100 个配对任务。

每条任务记录基线与研序两边的人工分钟、质量是否通过、返工次数，并明确 `same_scope`。只有范围一致且两边质量都通过的记录进入时间计算。

真实观察还必须给基线和研序两侧提供非空 `evidence` 引用，例如任务记录、commit、PR、运行报告或人工计时凭据。推荐使用 [`record`](MEASUREMENT_RECORDING.md) 逐侧写入，避免手工编辑 JSON 和意外覆盖。

```bash
python -m yanxu benchmark docs/benchmark-synthetic-example.json \
  --output runs/benchmark
```

输出 `benchmark.json`、`benchmark.md` 和可直接打开的 `benchmark.html`。

## 状态与验收

| 状态 | 含义 | 可否写收益结论 |
| --- | --- | --- |
| `DEMO_ONLY` | 合成数据，仅验证计算和展示 | 否 |
| `NOT_MEASURED` | 没有通过质量门的有效配对任务 | 否 |
| `EXPLORATORY` | 1–4 个真实有效配对任务 | 只能描述个案 |
| `OBSERVED` | 至少 5 个真实有效配对任务 | 只能描述该范围和样本 |

5 个样本是本项目的最低发布门槛，不代表统计显著。报告同时保留排除原因、基线/研序总人工分钟、中位数、加权时间减少率和返工次数；负值表示在该样本里变慢，不能隐藏。

## 面试表达

在没有真实样本前，可以说“实现了带质量门和样本边界的提效评测系统”。积累至少 5 个真实有效任务后，才可以说“在某类任务的 N 个配对样本中，观察到人工时间减少 X%，同时返工由 A 次变为 B 次”。不能写成全团队或所有研发任务都提升 X%。
